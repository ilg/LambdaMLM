# Design: Bounces and Complaints from SES Notifications

The second of the step 9 redesigns in the [modernization plan](../modernization-plan.md): "SES bounce and complaint notifications (SNS or event publishing) replace email-parsed bounces, which fixes [#22](https://github.com/ilg/LambdaMLM/issues/22) and enables [#11](https://github.com/ilg/LambdaMLM/issues/11). Email feedback forwarding stays on until this lands. Decide what happens to the vendored `bounce.py`."

It also covers the parts of the "handler dispatch" item that this needs.

An independent review checked this design against the code and AWS's documentation before it was published. Its findings are incorporated below.

## How bounces work today

- **Every post goes out once per recipient**, with `Source` set to that recipient's VERP address: `list+member=host+bounce@host`.
- **SES's email feedback forwarding** sends each bounce and complaint to that address. It's on for every identity, which is SES's default.
- **The receipt rule** stores the forwarded message, and the handler recognizes `+bounce@`.
- **`handle_bounce_to`** then:
  1. finds the list and member from the VERP address;
  2. classifies the message with the vendored Lamson analyzer (`detect_bounce`);
  3. records the result against the member, rescores them, and flags them as `bouncing` past the list's threshold.

**What's wrong with it:**

- **Complaints are never recognized** ([#22](https://github.com/ilg/LambdaMLM/issues/22)). SES forwards them as ARF reports, which the analyzer classifies as `unknown`, weight 0. So the complaint weight (3.0) that has been in the defaults since 2016 has never applied.
- **Classifying DSNs by parsing email is guesswork.** SES has already classified every bounce it forwards.
- **Concurrent writes lose updates.** Each bounce is a read-modify-write of the whole list config in S3, with nothing to stop two at once. A post to a large list can bring in several bounces within seconds. Each is handled by its own invocation, so updates to the same list can overwrite each other, including unrelated changes such as a subscription made at the same moment.

## What SES provides

Relevant facts from AWS's documentation, checked while writing this:

- **Event publishing.** A *configuration set* can publish `Bounce` and `Complaint` events to an SNS topic.
  - The configuration set must be named on every message it applies to (`ConfigurationSetName` on `SendRawEmail` and `SendEmail`; the pinned boto3 supports both).
  - SNS can deliver to an SQS queue, and the function can read that queue.
- **What an event says:**
  - `eventType`: `Bounce` or `Complaint`.
  - `mail.source`: the message's sender as we gave it, possibly with a display name.
  - `mail.destination`, `mail.messageId`, and `mail.tags` (including `ses:configuration-set`).
  - For a bounce:
    - `bounceType` is `Permanent`, `Transient` or `Undetermined`;
    - `bounceSubType` is one of `General`, `NoEmail`, `Suppressed`, `OnAccountSuppressionList` and others;
    - it also has `bouncedRecipients`, `timestamp` and `feedbackId`.
  - For a complaint: `complainedRecipients`, `complaintFeedbackType` (`abuse`, `not-spam` and so on), `complaintSubType`, `timestamp` and `feedbackId`.
- **Transient bounces** are published only after SES has given up retrying.
- **Feedback forwarding** can be turned off for an identity once bounce and complaint events are published to SNS by a configuration set that's applied to every message. For a message sent *without* such a configuration set, SES forwards the feedback by email anyway. So turning forwarding off on a list domain shouldn't affect anyone else's mail from that domain; the rollout checks this on staging.
  - It must be turned off with the v2 API (`PutEmailIdentityFeedbackAttributes`) or the console. The v1 `SetIdentityFeedbackForwardingEnabled` refuses unless identity notification topics are set, and this design doesn't use those.
- **Suppression lists.** Some bounces and complaints are generated by SES itself, without attempting delivery, because the address is on a suppression list:
  - bounce subtypes `Suppressed`, `OnAccountSuppressionList`, `OnTenantSuppressionList` and `EmailValidationSuppressed`;
  - `complaintSubType: OnAccountSuppressionList`.

  The account-level suppression list is shared by everything that sends from the account.
- **S3 conditional writes:** `PutObject` accepts `IfMatch`, and fails if the object's ETag has changed. The pinned boto3 supports it. A conflict can be reported three ways, and botocore retries none of them:
  - `412 PreconditionFailed`;
  - `409 ConditionalRequestConflict`, for a conflicting operation during the upload;
  - `404`, if the object was deleted meanwhile.

## Design

### The pipeline

```
SES send (with the stack's configuration set)
  → Bounce/Complaint event → SNS topic (the stack's)
  → SQS queue (raw message delivery) → the function (SQS event source, batches)
  → for each list in the batch: load once, record every event, save once (conditionally)
```

- **Why SNS then SQS, not SNS directly to the function:**
  - **Retries.** Mail from the receipt rule mustn't be retried, because a retry after a partial send delivers the post twice. That's why the function's asynchronous retries are 0. Recording a bounce is safe to retry. An SQS event source retries through the queue (visibility timeout, then a dead-letter queue after 5 receives), independently of the asynchronous setting.
  - **Batching.** A batch's events for one list are applied with one load and one save.
  - **Concurrency.** The event source's `MaximumConcurrency` (2, the minimum) limits how many invocations write list configs at once.
  - **Groundwork.** The queue fan-out redesign also puts an SQS event source on the function, so the dispatch below is where both land.
- **Why event publishing, not identity notifications:** identity notification topics are per-identity settings outside CloudFormation. On staging they'd sit on domains shared with other projects. A configuration set, its event destination, the topic and the queue are all stack resources.
- **Not EventBridge:** SES can publish to EventBridge too, but the plan names SNS, and SNS→SQS is the simplest well-trodden route to a queue.

### Stack resources

| Resource | Notes |
|---|---|
| `ConfigurationSet` (`AWS::SES::ConfigurationSet`) | Named after the stack. |
| `FeedbackEventDestination` (`AWS::SES::ConfigurationSetEventDestination`) | `MatchingEventTypes: [bounce, complaint]`, publishing to the topic. |
| `FeedbackTopic` (`AWS::SNS::Topic`) and its policy | Only `ses.amazonaws.com` may publish, with `aws:SourceAccount` and `aws:SourceArn` set to the configuration set's ARN. |
| `FeedbackQueue` and `FeedbackDeadLetterQueue` (`AWS::SQS::Queue`) and a queue policy | The policy allows only the topic to send. `SqsManagedSseEnabled: true`, since an AWS-managed KMS key would block SNS. Both keep messages 14 days: the dead-letter queue counts from the original enqueue time. Redrive to the dead-letter queue after 5 receives. |
| The topic's subscription | `sqs`, with raw message delivery, so each message body is the SES event itself. The topic isn't encrypted, since the AWS-managed SNS key would block SES. |
| An `SQS` event on `Function` | Batch size 10, a batching window of 30 s so that a post's bounces arrive together, `ReportBatchItemFailures`, `MaximumConcurrency: 2`. The queue's visibility timeout is 1830 s: six times the function's timeout plus the window, as AWS recommends. |
| An alarm on the dead-letter queue | Like the existing `Errors` alarm, whose description also changes: SQS-driven failures go to the dead-letter queue, not `FailedEvents`. |
| `LAMBDAMLM_CONFIGURATION_SET` | Set to the configuration set's name. |

**Ordering.** `Function` depends on the event destination, the subscription and the queue policy, and the event destination depends on the topic policy. Otherwise CloudFormation could start sending with the configuration set before events have anywhere to go, and they'd be lost.

`MatchingEventTypes` is spelled as `cfn-lint` requires (the property docs list `BOUNCE` and `COMPLAINT`).

### Sending

`mail.send_raw` and `mail.send_text` pass `ConfigurationSetName=settings.configuration_set` when it's set. That covers posts, moderator notices, command replies and invitations. Every message has to carry it for feedback forwarding to be turned off, and the refactor put every send in `mail.py` for exactly this reason.

The stack always sets it. If it's somehow empty, sending still works, but the deployment has no bounce handling at all: emailed bounces are dropped, and there are no events. So the function logs a warning when it starts without it.

### Dispatch

`lambda_handler` decides by the event's shape:

- **No `Records`:** the direct-invoke API, as today.
- **Records with `eventSource` of `aws:sqs`:** `handle_sqs_event`. Today that's only feedback, but the queue's ARN (`eventSourceARN`) is what will tell the fan-out queue's records apart later.
- **Any other `Records`:** `handle_ses_event`, as today. Receipt events have `eventSource: aws:ses`. Treating anything else with `Records` as SES keeps the tests' existing events working, and changes nothing for real ones.

### Handling feedback (`feedback.py`)

1. **Parse each record's body** as JSON, and read the `eventType`. Anything other than `Bounce` or `Complaint` is logged and acknowledged.
2. **Map the event to a response type**, or to nothing (ignored):

   | Event | Response |
   |---|---|
   | `Bounce`, `Permanent`, any subtype, including the suppression-list subtypes | `hard` |
   | `Bounce`, `Transient`, any subtype | `soft` |
   | `Bounce`, `Undetermined` | `unknown` |
   | `Complaint`, `complaintSubType: OnAccountSuppressionList` | `hard`: the message wasn't sent, because the address is suppressed. It isn't a complaint from the member. |
   | `Complaint`, `complaintFeedbackType` `not-spam` or `auth-failure` | ignored: the first says the message *isn't* spam, and the second is an authentication report |
   | `Complaint`, any other type, or none | `complaint` |

3. **Find the list username and host** from `mail.source` (after `parseaddr`). `list_and_member_for_verp` is split in two for this: `parse_verp(address)`, which does no S3 access, and `member_for_verp(list, address)`. That way a batch loads each list once, not once per event.
   - A source that isn't a VERP address is logged and acknowledged. Moderator notices, command replies and invitations are sent from the command address, and their bounces aren't recorded, as today.
   - So is a member who has since left.
   - The bounced or complained recipient isn't required to match the member: a DSN's `Final-Recipient` can be a forwarding target. The emailed path matched only on the VERP address too.

   Each event is logged with its list, member, `mail.destination`, type, subtype, `feedbackId` and source. (The end-to-end check that `mail.source` is the VERP address reads it from these log lines.)
4. **Group the batch's events by list, and update each list with `storage.update_list`** (from PR 1, below). It loads the list, records each event with `record_response` and its timestamp, and saves conditionally, reloading and reapplying on a conflict.
   - **A list that doesn't exist:** its events are logged and acknowledged. That means specifically S3's not-found: `storage` raises `ListNotFound`, a subclass of `UnknownList`, for a missing key.
   - **Any other S3 error, three conflicts in a row, or any other exception for that list** (bad YAML, say): the list's records are reported as batch-item failures, and the other lists' records still succeed. SQS delivers the failures again. After 5 receives they go to the dead-letter queue, whose alarm fires. Nothing is silently discarded because of an access problem or a bug.
5. **The response's time is the event's own `timestamp`**, when the ISP reported it, not the time the function handled it. It's converted to a naive UTC datetime like the ones stored today.
   - A retried or duplicated event lands on the same key in the member's `bounces` dict, so recording it twice has no effect. (That's why partial-batch failures, and redelivery in general, are safe.)
   - A delayed batch still counts on the right day.
   - The datetimes must stay naive: mixing naive and aware keys makes `bounce_score`'s sort fail.
   - Two *different* events for one member with the same millisecond timestamp would overwrite each other. That's improbable, and accepted.

   `record_response` takes an optional time for this, and `ListMember.add_response` passes it through. The emailed path keeps using "now".

### Emailed bounces

Once this is deployed, every message carries the configuration set, so SES sends its feedback as events. Two kinds of mail still reach VERP addresses:

- **Duplicates:** feedback forwarded while forwarding is still on.
- **Bounces of mail sent before the switch**, without the configuration set, which only arrive by email:
  - posts sent before the deploy (or during it);
  - at the production switchover, everything the Python 2 function sent.

  Asynchronous bounces, and SES's own soft-bounce give-ups, can arrive days later.

Recording forwarded mail would count every new bounce twice. So the handler no longer classifies mail to a `+bounce@` address:
- it logs it and deletes it, as it does for mail to a non-list address;
- it doesn't treat it as a post.

**The cost:** the bounces of mail sent before the switch are lost, up to a few days' worth. Complaints never counted anyway. See the owner questions for the alternative. (Nothing legitimate other than SES feedback reaches `+bounce@`: recipients only ever see SES's anonymized Return-Path, and list names can't contain `+`.)

**Turning off feedback forwarding** on each list domain is then housekeeping: it stops the duplicates arriving. It's a documented step for each deployment, using `aws sesv2 put-email-identity-feedback-attributes --email-identity DOMAIN --no-email-forwarding-enabled` or the console.

### Conditional writes everywhere

`load_list_config` already returns the ETag, and `List` keeps it. `save_list_config` passes `IfMatch` whenever it has one, and updates the list's ETag from the response. So every save fails, rather than silently overwriting, if something else changed the list since it was loaded.

`storage` turns all three conflict reports into one exception:
- 412 and 409 become `ListChanged`;
- 404 becomes `ListNotFound`.

`storage.update_list(host, username, change, attempts=3)` loads a list, applies `change`, saves conditionally, and reloads and retries on `ListChanged`.

Who does what on a conflict:

- **Feedback, and the emailed bounce path while it still records** (between PR 1 and PR 3), use `update_list`. A post's near-simultaneous bounces would otherwise make conflicts routine.
- **Email commands and API calls** don't retry. Replaying a user's command against a list that changed underneath it isn't obviously right.
  - A command replies "The list changed while your command was running. Please try again." instead of "Internal error.". `commands.run` recognizes `ListChanged`.
  - An API call returns `{'StatusCode': 409, 'Message': 'The list changed while this request was running. Try again.'}`. That keeps the `{StatusCode, Message}` shape the compatibility contract requires. An unhandled exception would return Lambda's own error payload instead.
- **The posting and moderation paths** never save a list.

Every save caller saves once per invocation today; the ETag refresh keeps a second save from failing if one is ever added. This changes behavior only when two writers race, which today silently loses one of the writes.

One harmless oddity: if botocore retries a PUT that had in fact succeeded, the retry fails with 412. Feedback just reapplies (idempotently); a command would say "try again" although its change was saved.

### Tests

**Unit tests:**
- **`FakeS3`:**
  - `get_object` and `head_object` return quoted ETags;
  - `put_object` accepts `IfMatch` and returns a new ETag;
  - a stale ETag raises 412;
  - tests can make it raise 409 or 404;
  - the `put` helper changes the ETag too, so a test can play a concurrent writer.

  The call log keeps its format, since tests pin it.
- **`FakeSES`** accepts `ConfigurationSetName`.
- **New tests cover:**
  - every row of the mapping table, including the suppression-list subtypes, `not-spam` and `auth-failure`;
  - sources that aren't VERP addresses, missing lists, departed members, and S3 errors other than not-found;
  - grouping a batch by list, with one list failing while the others succeed;
  - a conflict that succeeds on retry, and one that doesn't and reports batch-item failures;
  - 409 and 404 on save;
  - the command and API responses to a conflict;
  - the event's timestamp being used, and a duplicated event changing nothing;
  - dispatch;
  - `ConfigurationSetName` on every send, and none when unset;
  - mail to a `+bounce@` address being dropped;
  - a command or API conflict failing.

  The fixture events are built from AWS's documented examples.

**End-to-end:** the `bounce_and_complaint` scenario already sends to SES's bounce and complaint simulators through the list. It changes so that:
- it rewrites the `e2e-bounces` list before sending, so earlier runs' entries and flags can't stop delivery (a complaint now flags its member at once). That's the one exception to `e2e/lists.py`'s rule that setup never replaces a list, and its docstring says so;
- it waits for the entries to appear;
- it records their kinds: `hard` for the bounce simulator and `complaint` for the complaint simulator.

It also checks, from the function's logs, that `mail.source` really is the VERP address. That's the one fact above that comes from documentation examples rather than a guarantee.

A new scenario, `forwarding_fallback`, sends from a test inbox to the bounce simulator *without* the configuration set. It checks that SES still forwards the bounce to the sender by email. The rollout runs it after turning off forwarding on staging, to confirm the per-message fallback that makes turning it off safe for other senders and for a rollback.

The first staging deploy of PR 1 also confirms that S3 accepts the ETag exactly as `GetObject` returns it, in quotes: the subscription scenarios save lists.

### Compatibility

- **The list YAML is unchanged.** `!bouncekind complaint` entries appear for the first time. The tag and enum value have always existed, so the Python 2 function (production's fallback until the switchover is complete) reads them too.
- **Bounce and complaint scoring is unchanged:** the same weights, threshold and decay, and the same maximum per day. Complaints now reach it.
- **Stored times stay naive UTC datetimes.**

### Deliberate behavior changes

1. **Complaints count.** With the default weight (3.0) above the default threshold (2.0), one complaint flags the member as `bouncing`, and the list stops sending to them. That's what the defaults have said since 2016; it has just never happened.
2. **`not-spam` feedback is ignored.**
3. **`auth-failure` feedback is ignored**, and suppression-list feedback counts as a hard bounce.
4. **Mail to VERP addresses is dropped**, not classified, so the bounces of mail sent before the switch are lost.
5. **A bounce counts on the day the ISP reported it.**
6. **A save that races another write fails** instead of silently overwriting it: with "try again" for a command, and a 409 for the API.

## Order of work

**PR 1: conditional writes**
1. Add ETags and `IfMatch` to `FakeS3`, and `ConfigurationSetName` to `FakeSES`.
2. In `storage`:
   - `ListNotFound`;
   - `save_list_config` passes `IfMatch`, refreshes the ETag, and turns conflicts into `ListChanged`;
   - `update_list` retries.

   `handle_bounce_to` uses `update_list`.
3. The command and API responses to a conflict, with tests.

**PR 2: feedback handling**, not yet wired up in the stack

4. Split `list_and_member_for_verp`, and add `record_response`'s optional time.
5. Add `feedback.py`: parsing, mapping, grouping, per-list failures and batch-item failures.
6. Add dispatch and `handle_sqs_event`.

**PR 3: the switch**

7. Add the stack resources (with their `DependsOn`), the setting and the start-up warning, with the configuration set on every send.
8. Drop mail to VERP addresses.
9. Update the end-to-end scenario, add `forwarding_fallback`, and document the change in [Technical](../technical.md), [List Configuration](../list%20configuration.md) and [Setup](../setup.md):
   - how to turn off feedback forwarding (v2 API);
   - how to redrive the dead-letter queue (`aws sqs start-message-move-task`);
   - that clearing a member's `bouncing` flag doesn't help while their address is on SES's account-level suppression list.
10. Deploy to staging and run the end-to-end suite. Then turn off feedback forwarding on the staging list domains, and run it again, including `forwarding_fallback`.

**PR 4: remove the email bounce classifier**, after PR 3 has run on staging
- Remove `lamson_bounce.py`, `detect_bounce`, the flufl.bounce fixtures and their license, and the bounce golden files.
- `ResponseType` and its YAML tag stay: stored lists use them.

**The production switchover** (plan step 7) gains one step: after switching, turn off feedback forwarding on production's domain.

This is compatible with rolling back to the Python 2 function, provided staging's `forwarding_fallback` check passed:
- the old function's sends carry no configuration set, so their feedback is still forwarded by email, and the old function classifies it as it always has;
- events for mail the new function already sent keep reaching the new stack's queue, whose consumer stays active.

## Considered and not proposed

- **SNS straight to the function.** It's simpler, but the retries would follow the function's asynchronous setting (0, for the posts' sake). There'd be no batching, and no limit on concurrent writers.
- **Identity notification topics.** They're per-identity settings outside the stack, on domains that may be shared.
- **Message tags carrying the list and member.** SES restricts the characters tag values can hold, so tags couldn't carry addresses as they are. `mail.source` already carries the VERP address.
- **Keeping the Lamson classifier as a fallback.** With the configuration set on every message, there's nothing left for it to classify. A classifier that sometimes runs is harder to trust than one that doesn't exist.
- **Retrying email commands and API calls on a conflict.** See [Conditional writes everywhere](#conditional-writes-everywhere).
- **Notifying members or admins about bounces** ([#11](https://github.com/ilg/LambdaMLM/issues/11)). It's a feature request, and out of scope. `record_response` is where crossing the threshold is detected, so it's where #11 would hook in.

## Questions for the owner

1. **Complaints:** let one complaint flag the member as `bouncing` (the existing weight and threshold)? *Recommended.* The alternative is changing the default weight. Suppression-list "complaints" count as hard bounces, not complaints.
2. **Conditional writes for every save**, so that a racing command or API call fails instead of overwriting? *Recommended.*
3. **Removing the Lamson classifier** and its fixtures in PR 4, once PR 3 has run on staging? *Recommended.*
4. **Turning off feedback forwarding** on each deployment's list domains, as a documented manual step, for staging now and for production at the switchover? *Recommended.* It isn't needed for correctness (forwarded feedback is dropped), only to stop the duplicates.
5. **The bounces of mail sent before the switch:** accept losing them (a few days' worth at each switch)? *Recommended.*
   - The alternative is two phases. First, the new events are only logged, next to what the Lamson classifier makes of the same bounces, while emailed bounces keep being recorded. Then, after some days, events are recorded and emailed bounces dropped.
   - That loses nothing, and compares the two classifiers for free. But it's an extra deploy, and the production switchover would need the two phases as well.
